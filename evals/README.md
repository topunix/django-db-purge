# Adversarial evaluation of the MCP purge server

This directory documents the red-team suite for the three MCP tools
(`list_policies`, `preview_purge`, `execute_purge`). The suite lives in
`tests/adversarial/`. Each attack either proves the server blocks it or is
recorded as a finding with a severity and a proposed fix.

## Threat model

### Assets

- The rows in every model on the allowlist (`DB_PURGE_MCP_ALLOWED_MODELS`).
  Deletion is irreversible.
- The operator's intent: which policies exist, their bounds and row caps.
- The integrity of the call log, which is the audit trail for destructive
  actions.

### Actors

- A prompt-injected agent. The host's model is well behaved but text it reads
  (a ticket, a web page, a tool result) tells it to delete more than the
  operator intended. It can call only the three tools, with whatever
  arguments the injected text suggests.
- A malicious MCP client. It speaks the protocol directly, so it is not
  limited by what a model would plausibly send. It can send unexpected
  argument names, wrong types, huge values and control characters.
- A bystander writer. Another process changes rows in the database between
  a preview and an execute. It is not hostile to the server, but its writes
  must not turn an approved preview into a different deletion.

### Trust boundaries

- The operator, who writes Django settings, is trusted. Settings are the only
  place a model, column or filter is named.
- Everything that crosses the tool interface is untrusted: policy names,
  params, tokens and the argument names themselves.
- The token store is in process memory, so the process boundary is also a
  boundary: a token is valid only in the server that issued it.

### Out of scope

- A compromised host, process or database account. Anyone who can edit
  settings or run code in the server can purge directly.
- Network attacks. The transport is stdio, so there is no listener.
- Side effects of `ON DELETE CASCADE`. The row cap bounds matching rows, not
  cascade fan-out, as the tool docstrings state.
- A live agent loop. The suite replays a static payload corpus
  (`tests/adversarial/payloads.json`) and calls no model.
- PostgreSQL. The suite runs on SQLite only.

### Categories and the threats they cover

| Category | Threat |
| --- | --- |
| `token_lifecycle` | Deleting without a prior preview, by forging, reusing, replaying or retrying a confirmation token. |
| `parameter_binding` | Previewing one request and executing another: changed values, extra keys, type confusion and out-of-bounds values. |
| `row_set_fingerprint` | The data changing between preview and execute, so the deletion no longer matches what was approved. |
| `allowlist_scope_escape` | Reaching a model, column or filter the operator did not allow, through settings changes or extra tool arguments. |
| `row_cap` | Deleting more than the operator's cap, in one call or across many. |
| `protocol_injection` | Hostile text in names, values and arguments: prompt injection, SQL, control characters, homoglyphs and oversized strings. |

## Running the suite

Install the package with the MCP extra and the test dependencies, then run
the cases under the `adversarial` marker:

```
pip install ".[mcp]" pytest==9.1.1 pytest-django==4.14.0
pytest -m adversarial tests/adversarial \
  --junitxml=junit.xml --adversarial-json=results.json
python -m tests.adversarial.report results.json --check
```

The suite is hermetic and deterministic: no network, no sleeping (token
expiry is tested by patching `django.utils.timezone.now`) and no model calls.
`results.json` holds one record per case, sorted by id, with no timestamps,
so two runs produce identical bytes.

`python runtests.py` does not collect these files and does not need pytest.

To refresh the table below after changing the registry or the attacks:

```
python -m tests.adversarial.report results.json
```

## Recording findings

`tests/adversarial/registry.py` declares each case with `expected="blocked"`
or `expected="finding"`. A finding carries a severity (`low`, `medium`,
`high` or `critical`) and a proposed fix.

- A case declared `blocked` that is not blocked fails the suite. A person
  then changes it to `finding`, with a severity and a proposed fix. The
  suite never edits `dbpurge/` and neither does this change.
- A case declared `finding` that is now blocked also fails the suite, because
  the registry is stale. Change it to `blocked` and drop the severity and fix.
- The fix itself is a separate change to `dbpurge/`.
